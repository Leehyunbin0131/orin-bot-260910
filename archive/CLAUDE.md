# orinbot workspace — 작업 지침

ROS 2 **Jazzy** + **Gazebo Harmonic** (Ubuntu 24.04). 실제 로봇 없이 시뮬레이션 환경에서 개발 진행 중.

## 개발 환경 전제 조건

- ROS 배포판: Jazzy (`/opt/ros/jazzy`)
- Gazebo: Harmonic 버전 (`ros-jazzy-gz-*-vendor` 패키지로 설치됨, osrfoundation 저장소 미사용)
- 명령 실행 전 항상 환경변수 설정 수행: `source /opt/ros/jazzy/setup.bash && source ~/ros2_ws/install/setup.bash`
- `sudo` 실행 시 비밀번호 입력이 필요하므로, apt 패키지 설치는 사용자에게 요청할 것

## 핵심 아키텍처 원칙

- **Gazebo의 기본 DiffDrive 플러그인을 사용하지 않음**: 로봇 구동은 `ros2_control` + `gz_ros2_control` + `diff_drive_controller` 스택으로 처리합니다. 이는 실물 로봇으로 전환할 때 URDF의 `<hardware>` 블록만 교체하여 재사용성을 극대화하기 위함입니다.
- **센서 토픽 및 TF 프레임 명칭은 실제 하드웨어 규격에 맞춤**: Intel RealSense D435i의 경우 standard `realsense2_camera` (`camera_name:=camera`, `camera_namespace:=""`) 규격을 따릅니다. 시뮬레이션 전용 명칭을 임의로 새로 만들지 마세요.
- 속도 제어 명령 규격: `geometry_msgs/TwistStamped` (Jazzy 버전 `diff_drive_controller` 기본 규격).
- 로봇 치수 파라미터 관리: 모든 치수는 `orinbot.urdf.xacro` 상단 파라미터 블록에만 단일 정의합니다 (하드코딩 금지). 치수 변경 시 `orinbot_bringup/config/controllers.yaml` 파일의 `wheel_separation` 및 `wheel_radius` 항목도 함께 수정해야 합니다.

## 빌드, 실행 및 성능 검증

표준 `colcon` 빌드 방식을 사용합니다. 상세 상황별 실행 명령은 `README.md`의 "자율주행 (VSLAM + Nav2)" 절을 참고하세요.

**파라미터를 수정했거나 변경 사항이 있는 경우 반드시 `tools/` 도구로 정밀 측정하여 검증해야 합니다.**
측정 방법 및 왜곡 현상이 발생하는 주의사항은 `tools/README.md`에 정리되어 있으며, 현재 측정 기준선 수치와 직접 비교하여 성능 차이를 검증하세요.

## Gazebo 관련 주요 주의사항

- **Gazebo의 포인트 클라우드 토픽(`/camera/points`)을 직접 사용하지 말 것**: gz-sim은 좌표 데이터를 카메라 본체 좌표계 규약(x=전방)으로 채우면서 frame_id에는 광학 좌표계(z=전방) 명칭을 붙여 출력합니다. `optical_frame_id` / `gz_frame_id` 옵션을 변경해도 명칭만 바뀔 뿐 실제 데이터 축 변환은 수행되지 않습니다 (실측 확인 완료). 따라서 `depth_image_proc::PointCloudXyzrgbNode`를 이용하여 뎁스 영상과 camera_info 토픽으로부터 포인트 클라우드를 합성 생성합니다.
- 카메라 계열 센서에서는 `<camera><optical_frame_id>` 설정이 `<gz_frame_id>`보다 우선 적용됩니다. IMU 등 타 센서는 `<gz_frame_id>`가 적용됩니다.
- `XML Element[gz_frame_id] ... not defined in SDF` 경고 메시지는 libsdformat의 스키마 검사 경고일 뿐이며, gz-sim 내부에서는 정상적으로 값을 읽어들이므로 무시해도 됩니다.
- XML 주석 기호 내부에는 `--` 문자열을 사용하면 안 됩니다. (xacro 파싱 오류 발생)
- **`IncludeLaunchDescription`의 `launch_arguments`는 부모 스코프로 전파(Leak)됩니다**: 하위 런치 파일에 `use_rviz:=false`를 전달하면 상위 런치 파일의 `use_rviz` 변수까지 덮어씌워져 상위 RViz 노드가 실행되지 않는 문제가 발생합니다. include 실행 시 `GroupAction`으로 감싸서 변수 스코프를 격리해야 합니다.

## VSLAM / Nav2 관련 주요 실측 분석 사항

- **Nav2 라이프사이클(Lifecycle) 활성화 멈춤 현상 및 자동 복구 워치독 적용**: 개발 PC 환경에 네트워크 인터페이스가 3개 존재하는 경우 FastDDS 서비스 응답 매칭 지연으로 인해 `failed to send response to .../change_state` 및 `Failed to bring up all requested nodes. Aborting bringup.` 오류가 발생하며 멈춥니다.
  - `ROS_AUTOMATIC_DISCOVERY_RANGE=LOCALHOST` 설정이 필요하지만, 이 설정만으로는 완전히 해결되지 않습니다.
  - 증상이 치명적인 이유: 노드 프로세스는 정상 기동되어 있고 액션 서버도 확인되나 상태가 `inactive`/`unconfigured`여서 모든 이동 명령을 즉시 중단(ABORT)합니다. 겉으로는 "Nav2는 정상 실행 중이나 로봇이 움직이지 않음"으로만 관찰됩니다.
  - 이를 해결하기 위해 `scripts/nav2_startup_watchdog.py` 노드가 서버의 `is_active` 상태를 모니터링하다가 실패 감지 시 `manage_nodes`를 통해 **RESET 수행 후 STARTUP**을 자동 재요청합니다. (일부 노드가 활성화된 상태에서 STARTUP만 재전송하면 "already active" 오류로 실패하므로 반드시 RESET을 먼저 호출해야 함). 실측 결과 정지 감지 후 2초 이내에 5개 주요 서버가 모두 active 상태로 복구됩니다. 비활성화 옵션: `startup_watchdog:=false`.
  - **Jetson Orin 등 실물 기기는 코어당 연산 성능이 낮아 현상이 더 빈번하게 발생합니다.** 해당 워치독은 단순 편의 기능이 아니라 실기 배포 대비 항목입니다.
  - 워치독 노드에는 `use_sim_time` 파라미터를 적용하지 않습니다. 기동 모니터링 노드가 `/clock` 토픽에 의존하면 시뮬레이터가 시간 토픽을 발행하기 전까지 대기 상태에 빠질 수 있습니다.
- **RGB 및 뎁스 영상의 타임스탬프 비동기화 시 VSLAM 드립트 발생**: 848x480 resolution 30Hz 설정 시 Gazebo가 두 스트림을 동일한 타임스탬프 틱에 발행하지 못해 최대 0.13초의 시차가 발생했고, 제자리 360도 회전 시 위치 자세 오차가 최대 1.2m/87도까지 벌어졌습니다. 424x240 resolution 15Hz로 하향 조정하자 프레임이 정확히 일치하며 오차가 3mm / 0.03도로 대폭 감소했습니다.
- **VSLAM은 RGB 특징점 기반으로 동작함**: 뎁스 센서는 특징점에 3D 공간 좌표를 매핑하는 역할입니다. 무늬가 없는 밋밋한 벽면 앞에서는 뎁스 수치가 정확하더라도 오도메트리가 동작하지 않습니다. `worlds/generate_room.py`에서 벽면마다 고유한 텍스처를 생성하도록 구성한 이유입니다. 동일한 패턴을 재사용하면 서로 다른 장소를 동일 위치로 오인하여 잘못된 루프 클로저가 적용되고 자세 좌표가 수 미터 튀게 됩니다.
- **`rgbd_odometry`의 TF를 직접 사용하면 Nav2가 목표를 취소함**: Visual Odometry 연산 지연으로 인해 TF 스탬프가 평균 0.2초(최악 0.85초) 지연 발행되며, Nav2의 map->odom 조회가 미래 시간 외삽을 요구하여 조회가 실패합니다. 이에 따라 `publish_tf:=false`로 설정하고 `vodom_tf_relay.py` 노드가 50Hz 주기 및 미래 타임스탬프로 TF를 재발행하도록 처리했습니다.
- **`Grid/Sensor` 파라미터는 1로 설정함**: 0=레이저 스캔, 1=뎁스 영상. 0으로 두면 `/map` 지도가 모두 미탐색 영역으로 처리됩니다.
- **휠 오도메트리 보정 필요성**: Gazebo 물리 엔진이 원기둥 형상 바퀴의 접촉점을 안쪽 가장자리로 인식하여 실제 회전 반경에 오차가 발생합니다. `controllers.yaml`의 `wheel_separation_multiplier` 값이 이에 대한 보정치이며, 현재 40cm 큐브 로봇 기준 최적값은 **1.0863**입니다. 섀시 치수나 센서 배치를 변경할 경우 반드시 보정치를 재측정해야 합니다.
- **`behavior_server`에는 `enable_stamped_cmd_vel` 파라미터가 없음**: 항상 TwistStamped를 출력하며, 파라미터는 controller_server와 velocity_smoother에만 존재합니다.
- **`velocity_smoother` 필수 설정**: `stamp_smoothed_velocity_with_smoothing_time: True` 옵션이 필요합니다. `false` 설정 시 입력 명령의 타임스탬프를 재사용하여 `diff_drive_controller`가 "0.5초 이상 지난 오래된 명령"으로 판단하고 무시합니다.

## 센서 역할 분담 정의

치수, 주기, 좌표 프레임 등 변동 가능한 사양값은 본 문서에 직접 기재하지 않으며, 출처 파일(`orinbot.urdf.xacro` 상단 파라미터 블록, `d435i.urdf.xacro`, `rplidar_a2m12.urdf.xacro`, `generate_room.py`)을 참조합니다.
본 절에는 시스템 설계상의 **원인 및 근거**만 기재합니다.

- **라이다 스캔 평면은 지면 기준 0.49 m 높이에 위치하며, 이보다 낮은 장애물은 물리적으로 감지할 수 없음**: 지면 근처의 낮은 장애물은 D435i 카메라가 전담하여 감지합니다.
- **월드 내 다층 선반 3종은 센서 분담 테스트용 장치임** (`generate_room.py` 내 `SHELVES` 정의):
  두 센서의 감지 특성 차이를 검증하기 위해 선반 상판 높이를 다르게 설계했습니다.
  - `shelf_0`: 선반 상판이 라이다 스캔 평면에 **걸려** 2D 라이다만으로도 벽면 장애물로 정상 인식됨.
  - `shelf_1`: 선반 상판이 라이다 스캔 평면을 **통과함**. 라이다 수신 데이터상으로는 얇은 기둥 4개만 보이어 "통행 가능한 개활지"로 판단되나, 실제로는 상판이 튀어나와 있어 충돌 위험이 존재함. **STVL 3D 복셀 레이어가 없으면 Nav2가 이 공간으로 경로를 생성함.**
  - `shelf_2`: 측면이 막힌 구조 및 상단 물품 배치 (시각적 특징점 풍부한 구조).

## Nav2 구성 및 설계 검증 결과

- 컨트롤러 알고리즘은 **MPPI**를 적용하며, 파라미터 수치는 **Nav2 순정 기본값**을 사용합니다.
- 코스트맵 레이어 역할 분담:
  - `obstacle_layer` (2D): RPLIDAR `/scan` 데이터 전용. 360도 전방위 센서이므로 장애물 소거(Ray clearing)가 정상 동작함.
  - `stvl_layer` (3D 복셀): D435i `/camera/depth/points` 데이터 전용. 좁은 화각(87x58도) 특성상 회전 시 장애물을 빔으로 소거할 수 없으므로 시간 감쇠(Time decay) 방식을 적용함. `voxel_decay: 10.0` — 실측 결과 로봇이 등을 돌린 후 9초 이내에 장애물 비용이 100 -> 0으로 정상 소거됨.
  - `inflation_layer`: `cost_scaling_factor: 10.0`, `inflation_radius: 0.40`.
- **`footprint` 규격 설정**: 로봇의 실제 사각 형상(0.4m x 0.4m)을 명시합니다. 원형 근사(`robot_radius`)를 사용할 경우 0.8m 폭의 문을 통과 불가능한 영역으로 오인합니다. 또한 MPPI 제어기의 `CostCritic.consider_footprint: true` 옵션을 켜야 좁은 통로를 통과할 수 있습니다.
- **전역 코스트맵 해상도 설정 메커니즘**: `nav2_params.yaml`의 `global_costmap.resolution` 값은 무시됩니다. `StaticLayer`가 수신되는 `/map` 토픽 크기에 맞추어 코스트맵 크기를 재조정하므로, RTAB-Map의 `Grid/CellSize` 설정값(현재 0.05m, `slam.launch.py`)이 실제 전역 코스트맵 해상도가 됩니다. 로컬 코스트맵만 yaml 해상도 수치(현재 0.02m)를 그대로 적용합니다.
- **최소 통과 가능 통로 폭 기준: 0.70 m (제자리 회전 가능 여부 기준)** (2026-08-02 변경):
  - 단순 직진 주행만 고려할 경우 0.55m 폭 통로도 통과가 가능합니다 (실측 확인). 그러나 로봇은 막다른 통로에서 회차할 수 있어야 하며, 차동 구동 특성상 후진보다 제자리 회전을 우선 시도합니다 (Nav2의 `Spin` 복구 동작 포함).
  - **제자리 회전에 필요한 대각선 최소 폭 = √2 × 0.40 = 0.566 m.**
  - 실측 결과 (`tools/turnaround_test.py`, 기하학적 제자리 회전 검증):

    | 통로 폭 | 단방향 여유 | 중앙 제자리 회전 | 직진 중 허용 편심 | 회전 실패 현상 |
    |---|---|---|---|---|
    | 0.55 m | −8 mm | **실패** (86도 회전 후 325 mm 밀림) | ±75 mm | 항상 실패 |
    | 0.60 m | 17 mm | 통과 | ±100 mm | **100 mm 편심 시 21도 회전 후 실패** |
    | 0.70 m | 67 mm | 통과 | ±150 mm | 60 mm 편심 시 정상 확인 |
    | 0.90 m | 167 mm | 통과 | ±250 mm | 100 mm 편심 시 정상 확인 |

  - **0.60 m 기준이 탈락한 원인**: 직진 통과 중 주행 편심 허용 범위(±100 mm) 끝단에 위치할 경우 회전이 불가능해집니다. 즉, 정상 주행 중 정지했을 때 돌아설 수 없는 사각 상태에 빠집니다. 또한 단방향 여유 17 mm는 SLAM 위치 추정 오차(중앙값 21 mm, 90% 46 mm)보다 작아 위험합니다.
  - **따라서 SLAM 위치 추정 정확도와 통로 폭은 연계된 예산 관계입니다.** 정확도를 하향시키는 파라미터 변경(`Rtabmap/DetectionRate` 감소 등)은 회전 통과 여유를 직접적으로 감소시킵니다.
  - 테스트 환경 주의사항: **로봇을 통로 내부로 직접 순간이동시키지 마세요.** Gazebo 물리 엔진은 정적 물체와의 초기 관통 충돌을 밀어내지 않으므로, 벽면에 80 mm 묻힌 상태 그대로 회전을 시도하게 됩니다 (실측 확인). 반드시 외부 영역에서 직접 주행시켜 통로 내부로 진입해야 합니다.
- 속도 명령 전달 경로:
  `controller_server -> /cmd_vel_nav -> velocity_smoother -> /cmd_vel_smoothed`
  `사용자 수동 조종 -> /cmd_vel_teleop`, 두 입력은 `twist_mux`가 중재하여 `/cmd_vel`로 출력합니다.

## 자동 탐사 (프론티어 익스플로레이션)

지도 정보가 없는 상태에서 미탐색 영역을 자율 순회하며 지도를 작성합니다.

```bash
ros2 launch orinbot_navigation navigation.launch.py explore:=true
ros2 launch orinbot_navigation explore.launch.py     # 이미 시스템이 실행 중일 때 탐사 노드만 추가 기동
```

구현 파일: `orinbot_navigation/scripts/frontier_explorer.py`.
`/map` 토픽 데이터를 분석하여 "탐색 완료 구역과 미탐색 구역이 접하는 셀(프론티어)"을 군집화하고, `거리 - gain * 경계길이` 비용 함수가 최소인 지점으로 `NavigateToPose` 이동 명령을 전송합니다.
실측 결과: 10x8 m 크기의 방 전체를 약 3분 만에 매핑 완료했습니다.

외부 탐사 패키지를 사용하지 않은 이유: ROS 2 Jazzy 버전 공식 패키지 목록에 탐사 패키지가 부재하며, `explore_lite` 등 기존 패키지는 자체적인 `costmap_2d` 인스턴스를 추가 생성하므로 이미 발행 중인 `/map`만 활용하는 것이 Orin 자원 예산 측면에서 유익합니다.

**구현 과정에서 발견된 주요 실측 함정 사항**

- **`/map` 토픽의 QoS는 `RELIABLE + TRANSIENT_LOCAL`이며 RTAB-Map은 지도 갱신 시에만 발행함**: 기본 QoS(VOLATILE)로 구독 시 로봇이 정지한 상태에서 구독 노드가 연결되면 이전 지도 데이터를 수신하지 못하고 영구 대기 상태에 빠집니다. `/map`을 구독하는 모듈은 반드시 TRANSIENT_LOCAL로 맞춰야 합니다.
- **신규 목표 전송 시 Nav2는 기존 목표를 선점 취소(Preemption)하며 `ABORTED(6)` 상태를 반환함**: 이는 장애로 인한 실패가 아니므로 시퀀스 번호를 부여하여 이전 시퀀스의 반환 결과는 무시하도록 처리해야 합니다. 이 처리가 누락되면 정상적인 목표 지점들이 "이동 실패"로 등록되어 탐사가 조기 종료됩니다.
- **목표 수락 거절(`not accepted`) 상태는 해당 위치의 오류가 아니라 "서버 준비 미완료" 상태임**: `bt_navigator` 활성화 이전 등의 사유이므로 재시도 처리해야 합니다.
- **`NavfnPlanner`의 오차 허용 범위(`tolerance: 0.5m`)로 인해 목적지 미도달 상태에서도 성공 반환 현상 발생**: 목적지가 장애물 팽창 영역 내부 등 진입 불가 지역인 경우, 플래너가 허용 오차 범위 내의 가장 가까운 진입 가능 지점으로 경로를 단축하며 해당 지점이 현재 로봇 위치일 경우 제어기가 즉시 "Reached the goal!"을 반환합니다. 실측 결과: 0.70m 떨어진 위치에 대해 **253회 연속 "도착 완료" 반환**. 성공 수신 시 로봇의 실제 좌표 거리를 추가 검증해야 합니다.
- **안전 여유값(Margin)을 이용한 프론티어 필터링 금지**: 장애물 경계를 여유값만큼 팽창시켜 제외한 후 프론티어 군집 크기를 계산하면, 0.60m 폭 통로 입구의 유효 영역이 2개 셀로 줄어들어 최소 군집 기준 미달로 통로 전체가 탐사 대상에서 소거됩니다 (실측: 탐사 후보 6곳 -> 0곳 감소). 군집 크기는 원본 격자 기준으로 평가하고, 여유값은 "군집 내부의 최종 목표 좌표 지정"에만 활용해야 합니다.
- **진입 불가능한 미탐색 구역은 영구 블랙리스트로 제외 처리**: 장애물 뒷편 음영 지역 등 물리적으로 접근 불가한 영역에 대해 일시적 블랙리스트만 적용할 경우 탐사가 종료되지 않고 무한 대기 상태에 빠집니다.
- **"액션 서버 연결 완료" 상태를 Nav2 준비 완료 신호로 판단하면 안 됨**: 이는 `bt_navigator` 노드가 활성화되었다는 의미일 뿐, `planner_server`가 초기화 중이거나 전역 코스트맵이 `/map` 크기로 재설정되기 전이라면 **모든 목표 명령이 즉시 ABORT**됩니다. 이 시점의 실패로 지점을 평가하면 프론티어 전체가 블랙리스트에 등록되어 탐사가 시작되지 못합니다. `global_costmap/costmap` 토픽을 최소 1회 수신한 시점을 준비 완료 신호로 사용합니다.
- `STATUS_UNKNOWN(0)` 반환 상태 역시 노드 연결 상태 이상이므로 재시도를 수행해야 합니다.

**목표 좌표 선별 기준은 "진입 가능한가"가 아닌 "회차하여 돌아나올 수 있는가" 기준을 적용해야 함 (실측 결과)**

이 설정 변경 하나가 탐사 성능 전체를 좌우했습니다. 최소 여유 거리 `min_clearance` 수치를 내접 반지름 근처(0.18m)에서 **0.33m**로 조정한 결과입니다 (동일 월드, 스택 새로 기동 조건):

| 평가 항목 | 0.18 m (진입 가능 여부 기준) | 0.33 m (회차 출차 가능 여부 기준) |
|---|---|---|
| 전체 탐사 완주 시간 | 4526 초 | **188 초** |
| 후진 / 회전 / 끼임 횟수 | 38 / 30 / 19 회 | **0 / 0 / 0 회** |
| 후진·회전 복구 실패 | 30 회 / 26 회 | **0 회** |
| 최종 지도 형상 | 지도가 수 도 기울어지고 동쪽 구역 왜곡 뭉개짐 | **직각 상태 유지, 왜곡 없음** |
| 미탐색 구역 | 없음 (대신 지도 전체가 파손됨) | 0.60/0.55m 협소 통로 너머 구역만 잔재 |

- 0.18m 설정 시 발생한 끼임 현상은 모두 `x 4.4~4.7, y 1.6~3.7` 구역(통로 뱅크 너머의 협소 구역)에 집중되었습니다. 로봇이 벽면에 긁히며 회전하는 동안 휠 슬립이 발생하여 오도메트리가 깨졌고, 이 오차가 포즈 그래프 전체에 누적되어 지도 왜곡을 유발했습니다.
- **로봇이 정상 회차할 수 없는 공간에 진입시키면 단순 주행 실패를 넘어 전체 지도 데이터까지 손상됩니다.** 이것이 0.70 m 최소 통과 폭 기준을 적용해야 하는 강력한 근거입니다.
- 임계값을 외접 반지름(0.283m)이 아닌 0.33m로 설정한 이유는 위의 기하학적 제자리 회전 표를 참고하세요. 0.283m 수치를 그대로 적용할 경우 0.60m 폭 통로(중앙 여유 0.300m)가 진입 대상으로 잘못 판정됩니다.

## 충전 도킹 (opennav_docking)

구성 파일: `orinbot_navigation/config/docking.yaml`, `launch/docking.launch.py`.
도크 형상은 `generate_room.py` 의 `DOCK_*` 상수, 로봇 쪽 접점은 `orinbot.urdf.xacro` 의 `pogo_*` 상수입니다.

- **Nav2 순정 `opennav_docking` 을 사용하며 자체 구현하지 않습니다.** 실기 전환 시 `dock_database` 의 좌표만 바꾸면 되고, `/dock_robot` 액션 규격이 그대로 유지되어 BT 연동도 살아 있습니다. 검출만 자체 구현했습니다(`scripts/dock_marker_board.py`) — 이유는 아래 마커 항목 참고.
- **지도 좌표가 아니라 "지금 보이는 마커" 기준으로 붙어야 합니다.** SLAM 위치 오차가 중앙값 21 mm / 90% 46 mm 인데 충전 접점은 그보다 작은 오차를 요구합니다. 또한 코스트맵 팽창(0.40 m)이 벽 앞을 통째로 막아 일반 Nav2 주행으로는 도크 앞 0.7 m 까지밖에 갈 수 없습니다.
- **`fixed_frame` 은 `map` 이 아니라 `odom` 입니다.** 접근하는 몇 초 동안 SLAM 이 map->odom 을 수십 mm 씩 고쳐 넣는데, 그 보정이 그대로 목표 좌표의 점프가 되어 최종 정렬을 망칩니다.
- 마커는 ArUco `DICT_4X4_50`, 검은 사각형 0.10 m 짜리 **3장(id 1/0/2)을 좌우 0.16 m 간격으로** 벌려 붙입니다. 4x4 를 고른 이유는 424x240 해상도 때문입니다 — 테두리 포함 6칸이라 24 px 이면 읽히지만, 기본값 6x6 은 8칸이라 32 px 이 필요해 검출 거리가 크게 짧아집니다. 텍스처는 `generate_textures.py` 가 **검출기와 같은 cv2 라이브러리로** 생성합니다(비트 패턴을 손으로 옮기면 어긋나도 "그냥 검출이 안 되는" 상태가 되어 원인 추적이 어렵습니다).
- **마커를 3장 쓰는 이유가 이 설계의 핵심입니다.** 실물 스테이션에는 가이드 벽이 없어 최종 각도를 인식이 전적으로 결정합니다. 그런데 정면에 가까운 평면 마커 한 장은 자세 모호성 때문에 각도가 크게 흔들립니다(실측 1.3 m 에서 4.77도). 3장의 코너 12개를 하나의 보드로 함께 풀면(`cv2.aruco.estimatePoseBoard`) 그 흔들림이 사라집니다. **좌우로 벌리는 배치가 핵심입니다** — 세로로 쌓으면 yaw 개선 효과가 거의 없습니다. 구현은 `scripts/dock_marker_board.py`.
- **접근 방식은 `docking_mode` 인자로 고릅니다** — 기본값 `staged`(단계 분리, `scripts/staged_dock.py`), 비교용 `smooth`(Nav2 순정 `opennav_docking`). 액션 규격(`/dock_robot`, `/undock_robot`)은 같아서 상위 노드는 바꿀 것이 없습니다.
- **`staged` 는 정지 -> 측정 -> 보정 -> 정지 -> 재측정 을 반복합니다.** 차동구동은 옆으로 못 가므로 횡오차는 크랩 기동(회전 30도 -> 직진 e/sin30 -> 회전 -30도)으로 없앱니다. **크랩 부호를 뒤집으면 보정이 오차를 두 배로 키우고**(실측 76 -> 154 mm) 그 뒤 바깥 마커가 화각을 벗어나 검출까지 잃습니다 — 그래서 오차가 커지면 즉시 중단하는 감시를 넣었습니다.
- **`smooth` 에서만: 자세는 0.65 m 에서 확정하고 그 뒤로는 직진합니다.** 가까이 갈수록 마커는 커지지만 바깥 두 장이 화각을 벗어나기 시작하고, 마지막 몇 프레임이 가장 부정확합니다. 그런데 `docking_server` 는 마지막 검출값을 그대로 목표로 얼려서 들어가므로 **가장 나쁜 관측으로 마무리하게** 됩니다. 단일 마커 구성에서 이것 때문에 세로 오차가 −25 ~ +46 mm 로 흩어졌습니다. 확정 시점의 자세를 `odom` 프레임으로 한 번 변환해 두고 이후로는 시각만 갱신하며 같은 값을 내보냅니다.
  - **반드시 고정 프레임으로 변환해야 합니다.** 카메라 광학 프레임 값을 그대로 얼려 재발행하면 목표가 로봇을 따라 움직여 영원히 도달하지 못합니다.

**마커 높이는 직관과 반대로 낮으면 안 됩니다 (기하 계산).**
카메라는 지면 0.36 m 에서 15도 아래를 보고 컬러 화각이 69.4 x 42.8도이므로 시야는 수평 기준 +6.4도 ~ −36.4도입니다. 마커(한 변 s)가 화면에 완전히 들어오는 최소 거리는 `max((h + s/2 − 0.36)/tan6.4도, (0.36 − h + s/2)/tan36.4도)` 이고, 두 항이 같아지는 h = 0.316 에서 최소가 됩니다. "도크는 낮은 게 자연스럽다"고 h = 0.20 으로 두면 0.30 m 에서 이미 화면 아래로 잘려 나갑니다. 현재 h = 0.31.

| 성공률 | 5/5 | 3/3 |

- **세로가 한 자릿수 이상 좋아집니다.** 정지 상태 인식 정확도를 그대로 최종 자세로 가져가기 때문입니다. 곡선 접근은 그 정확한 측정값을 움직이면서 소비합니다.
- **가로는 크랩 기동의 분해능(직진 정지 허용 2 mm, 회전 0.23도)이 바닥이라 3~5 mm 아래로는 못 내려갑니다.** 허용치 ±34 mm 대비 무시할 수준이지만, 정직하게 적어 둡니다.
- 정렬은 **3회 안에 수렴합니다**. 실측 예: 접촉 예상 −75.4 mm -> −37.2 mm -> +0.1 mm.
- 시간이 약 3배 늘어납니다. 이것을 받아들이는 대신 "어느 단계에서 틀어졌는지 로그만 보면 안다"는 검사 가능성을 얻습니다.

**정렬 완료 판정은 축별 허용치가 아니라 "접촉 시점의 예상 횡오차" 하나로 합니다** (2026-08-02 변경).

횡오차와 각도오차는 독립이 아닙니다. 정렬을 마치고 직진하는 동안 각도는 그대로 횡오차로 바뀝니다:

```
접촉 시점 횡오차 = 정렬시 횡오차 − 직진거리 × sin(각도오차)
```

0.52 m 직진 기준으로 0.5도가 4.5 mm, 1도가 9.1 mm, 2도가 18 mm 입니다. 그래서 **예전 설정(횡 3 mm / 각도 0.5도)은 서로 안 맞았습니다** — 허용한 각도 0.5도만으로 4.5 mm 가 생기는데 그보다 작은 횡 3 mm 를 맞추려고 크랩을 반복했습니다(실측: −3.1 → +3.1 → +0.4 mm 로 헛돌아 회당 15~20초 손해).

지금은 `contact_lateral_budget: 0.015`(동판 허용 ±34 mm 의 절반) 하나로 판정하고, **크랩 보정량도 `lat` 이 아니라 이 예상값을 씁니다** — 그래야 고치지 않고 남겨 둔 각도가 만들 흘러감까지 같이 상쇄됩니다. 각도에는 느슨한 상한(`yaw_tolerance: 0.0175`, 1도)만 두는데 이건 정밀도용이 아니라 측정 이상 감시용입니다.

예측 모델의 실측 검증 (예상 → Gazebo 실제 가로 오차): **+10.4 → +5.5 mm, +0.9 → +0.9 mm, +0.1 → +1.2 mm.** 부호가 맞고 크기는 보수적입니다.

- **실측상 정렬 지점은 `approach_distance`(0.65 m)가 아니라 0.89~0.96 m 입니다.** `_goto_entry` 가 Nav2 로 진입점까지 가는데 Nav2 도착 허용 오차(±200 mm)만큼 못 미쳐 서기 때문입니다. 그래서 무보정 직진 구간이 0.36 m 가 아니라 0.61~0.66 m 이고, 남은 각도가 만드는 흘러감도 그만큼 커집니다. 위 식이 실제 `fwd` 를 쓰므로 판정 자체는 맞지만, 정렬 전에 0.65 m 까지 직진으로 좁히면 마커 정확도와 흘러감이 둘 다 좋아집니다.

**도크 기하 — 접점 높이가 가장 빡빡한 제약입니다.**
동판은 스테이션 바닥, 포고핀은 로봇 배면(하부)입니다. 그런데 동판을 바닥에 평평하게 깔 수 없습니다.

| 항목 | 높이 |
|---|---|
| 로봇 섀시 바닥 (= 접지고) | 0.060 m |
| 포고핀 브래킷 하단 | **0.045 m** |
| 동판 상면 | 0.040 m |
| 코스트맵 `min_obstacle_height` | 0.030 m |

브래킷은 **0.030 ~ 0.060 m 사이**에만 놓을 수 있습니다. 0.030 m 아래로 내리면 코스트맵이 장애물로 보지 않고 지나치는 물체(월드의 3 cm 문턱이 그 경계 시험용)에 그대로 걸리고, 0.060 m 위로 올리면 섀시 안에 들어가 동판에 닿지 않습니다.
좌우도 자유롭지 않습니다 — 구동륜 ±0.17, 캐스터 ±0.14 이므로 바퀴가 지나가지 않는 띠는 |y| < 0.11 뿐입니다. 동판이 바퀴 경로에 걸리면 로봇이 그 위로 올라타 버려 브래킷과의 간격이 그대로 유지됩니다.

**가이드 벽은 없습니다.** 실물 스테이션(MiR 형태 — 벽걸이 본체 + 경사 램프 위의 동판 스트립)에 가이드 벽이 없으므로, 각도와 좌우를 잡아 줄 물리적 수단이 없습니다. 그래서 3마커 보드의 정확도가 그대로 최종 정렬 품질이 됩니다.
접촉 허용치는 **핀 배열**이 동판(75 x 100 mm, 실물 규격) 위에 완전히 얹히는 범위입니다. 빼는 것은 브래킷이 아닙니다 — 커넥터가 6핀 2x3 / 피치 2.54 mm / male DIP 이라 전기적으로 닿아야 하는 면적은 **6.1 x 3.5 mm** 뿐이고, 30 mm 각 브래킷은 커넥터를 붙드는 구조물이라 동판 밖으로 걸쳐도 무방합니다(애초에 동판 상면보다 5 mm 위에 있습니다). 따라서 (동판 − 핀 배열)/2 로 **세로 ±48 mm / 가로 ±34 mm**.
브래킷을 접촉면으로 잡으면 ±35 / ±22.5 mm 가 되는데, 그러면 실제로는 닿아 있는데 "충전 안 됨"이 되어 있지도 않은 정렬 정확도를 요구하게 됩니다.
**실기 확인 필요**: 동판 상면 40 mm 에 브래킷 하단 45 mm 이므로 핀이 브래킷 아래로 5 mm 이상 나와 있어야 합니다. 2.54 mm 피치 포고핀의 스트로크는 보통 1.5~2.5 mm 라 자유 길이로 5 mm 를 메우고 **남는 만큼만 압축 여유**가 되고, 그 여유가 곧 바닥 높이 편차(램프 기울기, 동판 두께 공차) 허용치입니다.
(가이드 벽을 두는 설계도 시험해 봤는데, 통로 폭 0.44 m 는 로봇 내접 반경 0.20 m 의 2배보다 좁아 코스트맵에서 안쪽 전체가 `INSCRIBED_INFLATED_OBSTACLE` 로 칠해집니다. 즉 **가이드 벽을 두면 코스트맵 충돌 검사를 원리적으로 쓸 수 없습니다.**)

**충전 중 절전** (`auto_dock.py`, `power_save: true`)

도크에 붙어 있는 동안은 인지·항법이 필요 없으므로 재웁니다. 실기(Orin)는 6코어뿐이고 충전 전력도 유한해서, 놀고 있는 노드를 재우면 충전이 빨라지고 발열도 줄어듭니다.

- **죽이지 말고 멈춰야 합니다.** `rtabmap` 을 죽였다 살리면 DB 를 다시 읽고 재위치추정을 해야 하는데, 실측상 `localization` 모드는 CPU 25.1 -> 33.9 %p / 메모리 552 -> 604 MB 로 **오히려 더 씁니다.** `/rtabmap/pause` 는 포즈 그래프를 램에 둔 채 연산만 멈추므로 복귀가 즉시입니다 (대신 CPU 만 벌고 메모리는 그대로).
- Nav2 는 `lifecycle_manager` 의 **PAUSE(1) / RESUME(2)** 로 재웁니다 — 이 목적으로 만들어진 기능입니다. 실측으로 5개 서버가 모두 `inactive` 로 내려갑니다.
- `rgbd_odometry` 에는 pause 서비스가 **없습니다**(심볼 확인). 실기에서 이걸 재우려면 카메라 스트림 자체를 끊어야 합니다. 그 서비스 이름은 `extra_pause_services` / `extra_resume_services` 에 넣으면 코드 수정 없이 호출됩니다.
- **해제 순서가 중요합니다**: SLAM resume -> Nav2 RESUME -> **전역 코스트맵이 실제로 다시 나오는 것을 확인** -> 그 다음에 언도킹. 실측에서 RESUME 완료와 코스트맵 복귀 사이에 1.6초가 있었고, 그 사이에 나간 목표는 즉시 ABORT 됩니다. 코스트맵 확인 구독은 반드시 **VOLATILE** 이어야 합니다 — TRANSIENT_LOCAL 로 받으면 절전 직전의 옛 코스트맵이 즉시 들어와 준비된 것처럼 보입니다.
- 절전 중에는 도킹 명령을 막습니다. 인지가 죽은 채로 주행 명령이 나가면 아무것도 못 보고 움직입니다.

**절전 실측 — 시뮬레이터에서는 절감량을 잴 수 없습니다 (중요)**

`/clock` 이 1001 Hz 로 발행되고(`max_step_size: 0.001`, `real_time_factor: 1.0`), `use_sim_time: true` 인 rclpy 노드는 그것만 처리하느라 CPU 를 태웁니다. 같은 `battery_sim.py` 를 나란히 띄운 실측:

| 조건 | CPU |
|---|---|
| `use_sim_time: true` | **24.7 %** |
| `use_sim_time: false` | **0.0 ~ 2.3 %** |

따라서 시뮬레이터에서 잰 Python 노드 CPU 는 거의 전부 `/clock` 비용이고, **실기에는 `/clock` 자체가 없습니다.** `staged_dock` 89 %, `auto_dock` 87 %, `vodom_tf_relay` 25.7 % 같은 수치를 실기 추정에 쓰면 안 됩니다. (`MultiThreadedExecutor` 의 스레드 수 때문이라고 의심했으나 `num_threads=2` 로 제한해도 변화가 없었습니다 — 원인이 아니었습니다.)

절전으로 실제로 멈추는 것과 안 멈추는 것 (토픽 발행률 기준, 이건 신뢰할 수 있습니다):

| 토픽 | 절전 전 | 절전 중 |
|---|---|---|
| `/local_costmap/costmap` | 1.7 Hz | **정지** |
| `/vodom` | 15.0 Hz | **정지** |
| `/detected_dock_pose` | 15.1 Hz | **정지** |
| `/scan` | 9.9 Hz | 10.0 Hz (그대로) |
| `/camera/color/image_raw` | 15.1 Hz | 15.1 Hz (그대로) |
| `/camera/depth/points` | 9.0 Hz | 11.5 Hz (그대로) |

- **센서는 시뮬레이터에서 끌 수 없습니다.** Gazebo 센서를 ROS 에서 정지시킬 수단이 없습니다. 실기에서는 `realsense2_camera` / `rplidar_ros` 의 정지 서비스를 `extra_pause_services` 에 넣으면 코드 수정 없이 호출됩니다.
- `dock_marker_board` 의 `~/pause` 로 `detectMarkers` 를 멈춰 37.7 -> 32.0 % (5.7 %p). 나머지는 `/clock` 비용입니다.
- `rtabmap` 은 `pause` 후에도 24 % 를 남깁니다 — 새 노드 추가만 멈추고 구독·전처리는 계속합니다.
- `controller_server` 등은 `inactive` 인데도 8~9 % 를 씁니다 (실행기 스레드가 남음).

**결론: 실기 절감량은 실기에서 재야 합니다.** 시뮬레이터 수치로는 "무엇이 멈추는가"까지만 확인 가능합니다.

- **멀티스레드 실행기에서 상태 기계는 잠가야 합니다.** 절전 해제가 서비스 응답을 기다리며 수 초 블록하는데, `ReentrantCallbackGroup` 이면 그 사이 1 Hz 타이머가 다시 들어옵니다. 실측에서 `UndockRobot` 이 4번 발행되어 로봇이 그만큼 더 후진했습니다. 상태 플래그를 블록 **이후에** 세운 것이 원인이었고, 지금은 `threading.Lock` 으로 한 번에 하나만 돌게 합니다.

**실측으로 드러난 함정 (전부 "로그는 멀쩡한데 안 되는" 부류입니다)**

- **`docking_server` 의 `enable_stamped_cmd_vel` 기본값이 `false` 입니다.** 그대로 두면 `Twist` 를 내보내고 `diff_drive_controller`(TwistStamped 구독)가 조용히 무시합니다. 증상은 "도킹은 진행되는데 로봇이 제자리"입니다.
- **좁은 가이드 벽 안에서는 코스트맵 충돌 검사가 원리적으로 동작하지 않습니다.** 벽 사이 통로는 0.44 m 로 물리적으로 20 mm 씩 남지만, 코스트맵 내접 반경이 0.20 m 라 벽에서 0.20 m 이내 셀이 전부 `INSCRIBED_INFLATED_OBSTACLE` 로 칠해집니다. 즉 **깔때기 안쪽 전체가 "충돌"로 읽힙니다.** 일반화하면 로봇 내접 반경의 2배보다 좁은 통로에서는 이 검사를 쓸 수 없습니다. `dock_collision_threshold` 로 도크 근처를 제외해 보려 했으나 해결되지 않았습니다 — 0.45 에서는 매 도킹마다 재시도 1회(회당 7초 손해), 0.75 에서는 도크로부터 0.49 m 떨어진 지점의 충돌이 그대로 보고되며 재시도 4회 후 실패(`error_code 905`). 이 임계값은 "도크로부터의 거리"로 단순 동작하지 않습니다. 결론적으로 `use_collision_detection: false` 로 두고 접근 구간의 안전은 물리적인 가이드 벽에 맡깁니다. staging pose 까지 가는 길은 Nav2 가 자기 코스트맵으로 회피하므로 보호가 사라지는 구간은 마지막 0.7 m 뿐입니다. **실기에서는 그 구간을 위해 범퍼 스위치나 모터 전류 제한 같은 소프트웨어 밖의 보호 수단이 필요합니다.**
- **접점 접촉 판정에 SLAM 자세를 쓰면 안 됩니다.** `docking_server` 의 접근 루프는 `isDocked()` 뿐 아니라 **`isCharging()` 으로도 빠져나옵니다.** `battery_sim.py` 가 처음에 SLAM 자세(map→base_footprint) + 여유 0.15 m 로 충전을 판정했더니, 로봇이 아직 100 mm 앞에 있는데 "충전 시작"이 되어 접근이 거기서 끝났습니다(실측 세로 오차 중앙값 119 mm). 접촉은 물리적 사실이므로 Gazebo 지상 진실(`/ground_truth/odom`)로 판정해야 합니다. 그리고 그 허용치는 `docking_threshold` 보다 **커야** 합니다 — 작으면 "도착했는데 충전이 안 잡히는" 교착이 납니다.
- **`/world/<world>/dynamic_pose/info` 를 `tf2_msgs/TFMessage` 로 브리지하면 안 됩니다.** 그 메시지에는 프레임 이름을 담는 `header.data` 가 없어 `frame_id`/`child_frame_id` 가 전부 빈 문자열로 나옵니다(실측 확인). 어느 것이 로봇인지 구분할 수 없습니다. URDF 에 `gz-sim-odometry-publisher-system` 을 붙여 `nav_msgs/Odometry` 로 받으세요. 이때 gz 쪽 토픽 이름은 `<odom_topic>` 값 그대로이며 모델 이름으로 네임스페이스가 붙지 않습니다.
- **접근 종료 조건에 충전 여부를 넣으면 위치 정밀도를 잃습니다.** `docking_server` 의 접근 루프는 `isDocked()` 뿐 아니라 **`isCharging()` 으로도 빠져나옵니다.** 접점은 위치 허용치가 넓으므로(세로 ±48 mm) 목표보다 한참 앞에서 "충전 시작"이 걸리고, 접근이 거기서 끝납니다. 반대로 허용치를 좁히면 이번엔 도달했는데 충전이 안 잡혀 `Timed out waiting for charge to start` 로 재시도만 반복합니다(실측 4회 중 3회). 위치 정밀도와 충전 확인을 한 조건에 묶은 것이 원인이므로 역할을 나눕니다 — `use_battery_status: false` 로 두고 `docking_server` 는 확정된 목표까지 들어가는 것만, 충전이 실제로 시작됐는지는 `auto_dock.py` 가 `/battery_state` 로 확인하고 실패 시 다시 도킹합니다.
- **자세를 고정할 때 영상 타임스탬프로 TF 를 조회하면 안 됩니다.** 영상이 `odom` TF 보다 앞서 도착해 "Lookup would require extrapolation into the future" 로 매번 실패합니다. **`timeout` 을 줘도 소용없습니다** — 그 콜백이 단일 스레드 실행기를 잡고 있어 TF 리스너 콜백이 그 사이에 돌 수 없기 때문입니다. 조용히 실패해서 고정이 한 번도 안 걸린 채 예전 동작을 계속했고, 로그를 보지 않으면 "비슷하네"로 넘어갈 수치가 나왔습니다. 가장 최근 TF(stamp=0)로 조회하면 됩니다 — 영상 시각과 수십 ms 어긋나지만 접근 속도가 0.1 m/s 라 수 mm 수준입니다.
- **XML 주석 안의 `------` 는 xacro 를 깨뜨립니다.** 이 문서 위쪽에 이미 적혀 있는 함정인데 도크 브래킷 주석에서 그대로 재현됐습니다.

## 실물 기기(Jetson Orin Nano Super) 배포 자원 절감 가이드

타깃 보드 사양: 6코어 Cortex-A78AE 1.7GHz + 8GB **통합** 메모리 (CPU/GPU 공유).
코어당 연산 성능이 개발 PC(i7-14700K)의 1/4~1/5 수준이므로 리소스 여유가 적습니다.

**노드별 실측표, 상세 측정 방법 및 기각된 시도 항목은 `orin-resource-budget` 스킬 문서에 정리되어 있습니다.**
자원 절감을 위해 파라미터를 수정하기 전에 해당 스킬을 반드시 먼저 확인하세요. 이미 실측 후 기각 처리된 항목들(`controller_frequency` 하향, 전역 코스트맵 광선 거리 축소, Nav2 컴포지션 적용 등)이 정리되어 있습니다.

## RTAB-Map 메모리 관리 및 루프 클로저 실측 분석

- **`Grid/3D: true` 옵션이 메모리 사용량 증가의 주요 원인임**: 이 옵션을 비활성화할 경우:
  전체 메모리 **3.65 GB -> 1.66 GB** (rtabmap 단독 사용량 2656MB -> 914MB로 감소),
  CPU 사용량 **1.34 -> 1.16 코어**로 감소. 이에 따라 `map_3d` 런치 인자의 기본값을 **false**로 설정했습니다. Nav2는 2D `/map`만 참조하며 3D 장애물은 STVL 레이어가 담당하므로 자율 주행에는 영향이 없습니다. 3D 지도를 직접 시각화할 때만 `map_3d:=true` 옵션을 적용하세요.
- **`Rtabmap/DetectionRate` 파라미터가 가장 큰 CPU 제어 요소이나 기본값은 2.0 Hz를 유지함**: (`detection_rate` 런치 인자). 동일 월드 환경 실측 수치:

  | 평가 항목 | 2.0 Hz (현행 기본값) | 1.0 Hz |
  |---|---|---|
  | rtabmap CPU 사용량 | 25.1 %p | **15.5 %p** (−38% 절감) |
  | rtabmap 메모리 사용량 | 552 MB | **446 MB** (−106 MB 절감) |
  | SLAM 자세 오차 중앙값 | **0.021 m** | 0.027 m (+29% 증가) |
  | SLAM 자세 오차 90%값 | **0.046 m** | 0.052 m |
  | map->odom 최대 보정량 | **0.110 m** | 0.188 m (약 2배 증가) |

  자원 절감 효과(Orin 환산 0.5 코어 절감)는 크나, **본 시스템의 통로 통과 여유 공간은 곧 SLAM 위치 추정 오차 수치와 직접 연계됩니다.** 폭 0.70m 통로의 단방향 여유가 67mm인 상태에서 90% 오차 수치가 46 -> 52mm로 증가하는 것은 통행 안전 예산을 직접적으로 소모합니다. 따라서 Orin 환경에서 CPU 자원이 극도로 부족한 경우에만 `detection_rate:=1.0` 옵션을 적용하세요.
- **`Rtabmap/MemoryThr` 파라미터는 작업 메모리의 "노드 개수"만 제한함**: 점유 격자 캐시는 노드 개수와 별개로 전체 지도에 대해 누적되므로, 300 노드로 제한하더라도 메모리가 지속 증가했습니다. 격자 설정(`Grid/3D`, `Grid/RangeMax`)을 제어해야 합니다.
- **`Reg/Strategy: 2` (영상 + ICP 융합) 옵션은 3D 격자를 끄면 비용 부담 없이 적용 가능함**: 시각 영상으로 루프 클로저를 탐색한 후 라이다 스캔 ICP 알고리즘으로 기하학적 정밀도를 검증하므로, 벽면 패턴이 유사한 실내 환경에서 오조합 루프 클로저 발생을 획기적으로 방지합니다.
  실측 결과 (동일 왕복 주행 구간): map->odom 최대 보정량 **1.317 m -> 0.141 m**, SLAM 위치 오차 90%값 0.323 -> 0.056 m로 개선됨.
- **벽면 텍스처 재사용 금지**: 통로 구역을 추가하면서 기존 텍스처를 재사용한 결과(`wall_05` 3곳, `wall_06~10` 각 2곳 지정) 위치 추정이 크게 흔들리는 현상이 발생했습니다. `generate_textures.py`의 `N_WALL_SEGMENTS` 수치를 필요한 만큼 확장하여 모든 벽면에 고유한 고유 번호 텍스처를 부여해야 합니다. (현재 28개 생성, 26개 적용 중).
- **컬러 영상을 RTAB-Map 특징점 입력으로 사용하려면 정합된 뎁스 영상이 필요함**: `camera_color_optical_frame` 좌표계는 depth/infra1 프레임 위치에서 **15 mm** 이격되어 있습니다 (실물 D435i 카메라 규격과 동일). 정합 처리 없이 컬러+뎁스 영상을 전달하면 특징점에 잘못된 깊이 수치가 매핑됩니다. 실기 환경에서는 `align_depth.enable:=true` 옵션으로 `/camera/aligned_depth_to_color/image_raw`를 사용합니다. 시뮬레이션에서 이를 처리하려면 컬러 프레임 위치에 뎁스 센서를 추가 배치해야 합니다 (렌더링 4개 필요).
- **실물 기기 IR 프로젝터 주의사항**: D435i 센서의 IR 도트 패턴이 infra 영상에 촬영되는데, 로봇과 함께 이동하므로 고정된 월드 특징점으로 작용하지 못합니다. VSLAM 입력으로 infra 영상을 사용할 때 `emitter_enabled:=false` (뎁스 품질 일부 하향) 또는 `emitter_on_off:=true` (프레임 교대 토글, 프레임률 절반 하향) 적용을 검토해야 합니다. 시뮬레이션 환경에는 IR 프로젝터가 모사되어 있지 않으므로 본 문제가 관찰되지 않습니다.

## EKF (휠 엔코더 + IMU) 센서 융합 분석

- 구성 파일: `orinbot_bringup/config/ekf.yaml`. 휠 엔코더의 선속도 `vx`/각속도 `vyaw` 및 D435i 자이로 센서의 각속도 `vyaw` 수치만 융합합니다. 엔코더 **절대 위치**, IMU **자세(Orientation)**, IMU **가속도** 수치는 드리프트 누적, 자력계 부재, 평면 주행 시 노이즈 우세 현상으로 인해 의도적으로 융합에서 제외했습니다.
- **`controllers.yaml`의 `enable_odom_tf` 옵션은 반드시 false로 설정해야 함**: EKF 노드와 컨트롤러가 동시에 TF를 발행하면 동일한 `odom -> base_footprint` TF를 두 노드가 중복 발행하여 좌표계가 꼬이게 됩니다.
- **EKF 노드는 반드시 차동 구동 컨트롤러가 정상 기동된 이후에 기동해야 함**: `robot_localization`은 `use_sim_time:=true` 설정 시 시계 토픽이 유효해질 때까지 `Waiting for clock to start...` 메시지와 함께 대기하는데, Gazebo 시뮬레이터보다 먼저 기동될 경우 **대기 상태에서 영구히 빠져나오지 못하는 현상이 발생합니다.** 노드는 정상 작동 중이나 `/odometry/filtered` 및 TF가 출력되지 않아 TF 체인이 끊어지고 RViz에서 로봇 포즈가 튀며 매핑이 파손됩니다. `sim.launch.py` 내의 `diff_drive_then_ekf` 이벤트 핸들러가 이를 방지하기 위한 순차 기동 로직입니다.
- 별도 외부 IMU 센서(HandsFree A9 등) 추가의 실익은 적습니다. 본 시스템은 자이로의 `vyaw` 단일 축만 활용하는데 외부 센서 역시 동급 MEMS 규격이며, 차별점인 자력계는 실내 환경 및 모터 자계 간섭으로 인해 사용이 불가능합니다. 각속도는 강체 내 위치와 무관하게 동일하므로 카메라 모듈에 내장되어 있는 점 역시 불리하지 않습니다.

## 잔여 장애물 지도 소거 메커니즘

- **로컬 코스트맵**: 실시간으로 갱신됩니다. `obstacle_layer`는 라이다 레이 트레이싱으로 즉시 비워지며, `stvl_layer`는 `voxel_decay: 10.0` 설정에 따라 10초 후 자동 감쇠되어 소거됩니다 (실측: 장애물 비용 100 -> 0 소거까지 약 9초 소요).
- **RTAB-Map `/map` 토픽**: 즉시 소거되지 않습니다. 포즈 그래프의 각 노드가 생성 당시의 격자 정보를 보존하고 있어 소급 수정되지 않으며, 해당 위치를 다시 통과하며 신규 노드가 누적 생성되어야 지도가 갱신됩니다.
- **주의사항**: `static_layer`에 등록된 유령 장애물은 라이다 레이로 비워져도 소거되지 않습니다. 코스트맵 레이어가 최댓값(Max) 방식으로 합쳐지기 때문입니다. `localization:=true` 모드로 운용 중일 경우 지도가 고정되어 영구히 잔재합니다.

## 프로세스 cleanup 및 정리 시 주의사항

- **이전 실행의 `parameter_bridge` 프로세스가 남아있으면 신규 Gazebo에 자동 연결됨**: gz-transport 통신 라이브러리가 신규 서버를 자동으로 탐색하여 연결되므로, 브리지 프로세스가 중복 기동되어 `/clock` 토픽을 두 곳에서 각각 재발행합니다. 이로 인해 타임스탬프 순서가 꼬이면서 모든 노드에서 `Detected jump back in time. Clearing TF buffer` 경고 메시지가 반복되고 TF 버퍼가 계속 비워져 Nav2 및 RTAB-Map 조회가 전면 실패합니다. 증상이 "간헐적 정지"로 나타나 원인 추적이 어렵습니다.
- **따라서 시스템 재기동 직후 `ros2 topic info /clock` 명령의 `Publisher count` 수치가 1인지 반드시 확인하세요.** 2 이상일 경우 잔여 프로세스가 존재합니다.
- PID를 개별 지정하여 종료하면 누락되기 쉬우므로 패턴 기반 프로세스 탐색을 수행하되, 자기 자신 프로세스는 제외하도록 구성해야 합니다 (`pkill -f` 명령은 자기 자신의 명령줄에도 매칭되어 스크립트를 중단시킬 수 있음):
  ```bash
  ps -eo pid,args | grep -E '[p]arameter_bridge|[g]z sim|[r]tabmap|[_]server' \
    | awk -v me=$$ '$1 != me {print $1}' | xargs -r kill
  ```

## 개발 시 주요 주의사항

- URDF 모델이나 월드 파일 수정 후에는 Gazebo 프로세스를 완전히 종료한 뒤 재기동하세요. (`gz sim` 서버 프로세스가 배경에 남아있으면 수정 이전의 기존 모델이 재사용됨). `pkill -f` 대신 위 `ps | awk` 방식을 사용하세요.
- 파라미터만 수정했을 경우 전체 시스템을 내리지 마세요. 시뮬레이션 및 SLAM 노드는 기동 상태로 유지한 채 Nav2 노드만 종료 후 `ros2 launch orinbot_navigation nav2.launch.py` 명령으로 단독 재기동하면 됩니다 (약 45초 소요. 전체 재기동은 3분 이상 소요됨).
- 컨트롤러 기동이 실패할 경우 `ros2 control list_controllers` 명령으로 상태를 먼저 점검하세요.
- 카메라 영상 출력이 생성되지 않을 경우 월드 SDF 파일 내에 `gz-sim-sensors-system` 플러그인이 포함되어 있는지 확인하세요.
